# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Chrome Extension (Manifest V3) called "Xync Agent Setter". It extracts authentication cookies/headers and user profile data from supported exchanges (currently Bybit `www.bybit.com`, HTX `www.htx.com` and MEXC `www.mexc.com`) and sends them to the Xync backend (`api.xync.net/public/set-agent`) to establish an agent relationship. The panel branches per host; adding an exchange means adding a host branch in `panel.js` and the host to `ALLOWED_HOSTS` in `background.js` plus `host_permissions` in `manifest.json`.

## Development

No build system, bundler, or package manager. The extension runs from raw source files.

**To develop/test:** Load the extension directory as an unpacked extension in `chrome://extensions/` with Developer mode enabled.

## Architecture

Two independent features: agent setup (`background.js`, `panel.*`) and the parse + filters on Bybit's P2P pages (`hook.js`, `content.js`, `content.css`, `filter.js` in the panel, the Xync API proxy and request blocking in `background.js`).

The interface is a side panel, not a popup: the icon opens it (`setPanelBehavior`), one for the window, and it stays when the focus leaves, so nothing it does has to move to the worker. It's the same panel on every tab, so it can't be disabled per tab: on Telegram's tab that would end the login. In exchange it follows the active tab itself.

- **`background.js`** — Service worker that (1) gates the extension icon to only be enabled on allowed hosts (`www.bybit.com`, `www.htx.com`, `www.mexc.com`) via `chrome.tabs.onUpdated`/`onActivated`, and (2) uses `chrome.webRequest` to capture HTX's signed `user/info` request (method, headers incl. `Vtoken`, body) into `chrome.storage.session` so the panel can replay it.
- **`panel.js`** — Core logic triggered by button click, branched per host. **Bybit:** reads `secure-token`/`deviceId` cookies and POSTs to the Bybit personal-info API. **HTX:** reads the `HB_SSO` cookie and replays the captured `user/info` request (HTX signs requests with headers we can't rebuild, so the OTC page must have been opened once to capture it). **MEXC:** reads the `u_id` cookie (session token) and `x-mxc-fingerprint` cookie (replayed as the `device-id` header), then hits two endpoints — `api/platform/p2p/api/user` (GET) for `realName` + `nickName`, and `ucenter/api/user_info` (POST) for the numeric `uid` (its `digitalId`; the P2P endpoint only exposes a `memberId` hash). A `chash` value is also needed but its carrier is not yet identified — currently forwarded only if present as a cookie. Each branch builds `{host, uid, auth, profile}` and POSTs it to the Xync backend.
- **`panel.html`** — Inline CSS: agent setup's button and, on USDT/RUB P2P pages, the filter; a hint on sites the extension has no rights to.
- **`hook.js`** — Runs in the page's MAIN world at `document_start`, reads the page's own `item/online` responses (XHR and fetch) and posts `[{id, nick, fast}]` to the window (`fast`: Bybit's "Fast release"/"Fast payment" on the ad: the backend then drops a wrong `abuser=long` from its parse); `null` off `/*/p2p/{buy|sell}/USDT/RUB` (checked per listing: the manifest matches all of `/p2p/`, Bybit switches currency without a page load). Ad ids must stay strings. With a filter saved in `localStorage.xyncFilter` it swaps the list in the response: fetches the whole book (up to 600, by the page's own headers, in pages of 300, Bybit's maximum: 301 is refused with `912120002 Invalid request parameter`; the page's request waits for the whole book, and past its timeout, 30 to 65 s, the page stays empty), gets the passing ids from `content.js`, gives the page its slice with a new `count`. So Bybit renders the result itself: rows, pagination and "Buy" are its own. An XHR can't wait, so its events are withheld and replayed. The filtered book lives 60 s, for page turns and the page's refreshes. If anything fails the page gets its original response.
- **`content.js`** — Isolated world. Asks `POST /ext/ad-tags` and puts a box under each row: the parse, ready-made by the backend (`cond_chips`: `{field: label}`), and where it stands. Rows are found by content, not class names: Bybit's are hashed. So a change in Bybit's markup only matters if the nick stops being a separate text node. Rebuilds everything on any DOM change, because the page reuses rows for other ads, so a button's state lives in the ad (`busy`, `err`), and every minute, for the ages. Keeps the filter set in the panel: a change reloads the page (its list can't be re-requested from outside). The outcome goes on the extension's badge, the number of ads a filter kept (only about 4 characters fit, `kept/all` is in the panel), `…` while it's running, `!` on any error, whose text the panel shows; an error stays till the page reloads or a button's retry succeeds. Which ads pass is decided only by the backend: with a filter an ad is in the `ad-tags` reply iff it's parsed and fits, so ads without a parse are hidden under a filter.
- **The box** — `COLUMNS` in `content.js` is the layout: a `td` under each of Bybit's five columns, by the question it answers (who's the maker, is the price what it seems, what sum, how to pay, what's asked of the buyer), and in each a grid of slots. Every slot exists in every ad, empty ones are invisible, so a field sits at the same spot whatever else was parsed and all boxes are of one height. Empty means "not said", so a parse with no limits is just an age. A new parsed field needs a line in `cond_chips`, a slot in `COLUMNS` and a color in `content.css`. A sibling row, not chips inside Bybit's cells: those are the page's to re-render, and their heights differ, the spots would too.
- **Buttons of the box** — Not in the reply: the ad isn't in the DB, `🔄` → `POST /ext/ad-load`, a running agent gets it from the exchange. `tags: null`: `Parse` → `POST /ext/ad-parse`, saved at once. Parsed over 5 minutes ago: the same as `ReParse`. `{}` without `at`: the ad has no condition, nothing to do. After a click the whole listing is asked for again: a parse is the condition's, other ads on the page may share it. Both are admin-only on the backend; for anyone else the refusal shows in the row. The reply waits for the parse: a pending message keeps the worker alive, 100 s is checked, the 30 s `fetch()` limit of the docs doesn't apply.
- **`filter.js`** — The panel's filter: asks `content.js` for the state (`filter`, `error`, `count`; no reply: not a filter page) and `GET /ext/cond-filters` for the options; a value clicks through only → except → off. Asks again on a tab's switch or load and on every `badge` message: `runtime.sendMessage` from a content script reaches the panel too. Clicks not applied yet survive all that, a new filter of the page replaces them. The login lives here too.
- **`content.css`** — Cuts the listing down to the filter (Buy/Sell and the coin are part of it), the ads and the pager, under Bybit's header and P2P menu, before the first paint. Unlike the rows, these blocks have stable class names. An allow-list where banners differ with the login, so ones never seen anonymously go too. `tr.new-user-ads` is the same "Recommended" block as the carousel row: which one renders depends on the side. Hidden blocks stay in the DOM, so `placed()` skips text that isn't rendered: a nick there would take its row's tags. Bybit's first-load skeleton is forced visible: it's hidden by its own parent, and the filter holds the list for seconds. Each slot's color comes from its field. `#root`'s `min-width` and the list's fixed width are lifted so that the list shrinks next to the panel: otherwise it's the "Buy" button that goes. Bybit's columns are given new widths while the boxes are there, the payment is the busiest and was the narrowest; a box's `width: 0` keeps its text from moving them.
- **Cutting requests** (`CUT` in `background.js`) — What's hidden mostly isn't loaded at all. Chrome's rules can't match the page's address, so they are session rules by tab, set on each full load of Bybit: static ones would take the support and popups off all of Bybit. `initiatorDomains` is what stops them from breaking other sites' Google login when the tab moves on. Moves inside the P2P app don't reset them: from the list to an order, support stays off till a reload. A rule that loses the race to the page's first requests only lets them through: what shows is hidden by `content.css` anyway, which is why both exist. The Notice dialog is an "activity" of `configuration/activity/list`, the same list feeds the banners; without it `isActivePop` stays false, which only holds back coupon prompts. Failed chunks and fetches show in the console as unhandled rejections: expected. Before adding a line: `window.sensors` (`data-core`) is called directly by the page, and Akamai, `finger_device.js`, `t1.js`, turingfraud and compliance are what login and orders rely on, so these stay.
- **Login** — The Xync API needs a JWT. A 401 shows `!` and a login button in the panel: `/auth/tg-start` → the bot → polling `/auth/tg-poll` from `filter.js`, then reloading the tab. Closing the panel drops the waiting login. `background.js` keeps the token from the `Authorization` response header in `chrome.storage.local` and sends it as is. The JWT lives 15 minutes: the middleware lets an expired one through and renews it, but only in a cookie, so `POST /ext/ad-tags` also returns the current token in that header. One login is enough.

**Data flow:** Button click → get active tab → per-host: read cookies (HTX also replays the captured `user/info` request) → obtain user profile → POST to `api.xync.net` → display expiration date (ru-RU locale).

## Key Details

- Vanilla JavaScript (no TypeScript, no framework); `minimum_chrome_version` 117 (`world: MAIN`, `Object.groupBy`)
- Live `bybit.com` doesn't open from a headless browser, but does from a visible one (`headless=False`), and its listing needs no login: check `hook.js`/`content.js` there with `api.xync.net` mocked. Failure paths are checked on a fixture of the page: in full Chromium with `--load-extension`, `ctx.route` for `bybit.com` and, with `PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1`, for `api.xync.net` called from the worker. A real side panel opens by a real click on a button that calls `chrome.sidePanel.open` in an extension page; Playwright doesn't list it, `--remote-debugging-port` does (`/json/list`), and it's driven over that with `Runtime.evaluate`. With a fixed `viewport` the page doesn't shrink beside it: use `no_viewport=True` and `--window-size`. A debugger keeps a worker alive, so its lifetime is only seen with a plain Chrome and no debugger
- Permissions: `activeTab`, `cookies`, `webRequest`, `storage`, `declarativeNetRequest`, `sidePanel`; host permissions restricted to `bybit.com`, `htx.com`, and `api.xync.net`
- No tests, no linter, no formatter configured
